## 10. Reviewer Notes

1. **Real-DB tests cannot run by default.** Treat the 11 skip-marked tests as unproven in CI. They also look unsafe on a shared database: `Test_V3`/`Test_V5` call `ClaimNextAsync` up to 200 times and add every claimed id (including other people's queued tasks) to the cleanup list, which then flips them to `Cancelled`; the sweep tests sweep every `Running` row. Document that they must only be pointed at a scratch database (same hazard pattern exists in the older sweep/claim suites).
2. **§13 deviations.** `LogHygieneTests` and `TaskQueueSweepTests` were not extended; new classes were created instead (acceptable, but SC-9 evidence is Api-side only).
3. **Cancel latency before the watcher exists.** The watcher is created after `SearchCandidatesAsync`, candidate filtering and the resume skip loop (`KeywordSearchTaskProcessor.cs:114-173`). A cancel during that phase is honoured only after it finishes (up to one poll interval later). The flag is not lost, but §2.2/V6 latency ("poll interval + longest in-flight step") does not cover a slow candidate query on a 310k-file index.
4. **Cancel observed at the tail.** If the flag is seen while the last candidates are in flight, `Parallel.ForEachAsync` may still throw `OperationCanceledException` after every candidate was dispositioned; the task would then end `Cancelled` with processed == total instead of `Completed`. Harmless (results are complete and labelled `IsPartial`), but differs slightly from the §2.4 wording.
5. **Cancel accepted but task completes.** A 202 `Cancelling` followed by `Completed` leaves a `TaskCancelRequested` audit row with no `TaskCancelled` row. This is the §2.4 behaviour; auditors should be told.
6. **SP lock path.** `task_queue_cancel_req` forces `IX_task_queue_status_submitted_at` and filters by `task_queue_id`, so it range-scans the Queued/Running index entries rather than seeking the PK. Intentional (same lock order as claim, no deadlock in a 300 x 1500 scratch race) and the Queued/Running set is small, but it can briefly wait behind an in-flight claim lock.
7. **Watcher disposal.** `CancelRequestWatcher.Dispose` blocks synchronously (up to 5 s) from an async method. If the wait times out the CTS objects are disposed under a still-running loop; the loop would log a warning at worst. Low risk.
8. **Docs left for merge.** The Design doc section 10 addendum and the decomposition-guideline entry (§4, §14 Q1) are not done (no `CAS-056` in `coding-agent/decisions/spec-decomposition-guideline.md`). §14 Q2-Q5 remain open owner questions. Spec frontmatter `status` is still `review`.
9. **Controller XML summary.** `TaskManagerController.cs:12-13`: the CAS-030 sentence lost its terminating period when the CAS-056 line was added; cosmetic.
10. **Unrelated failures.** Three `FileIndexRepositoryTests` (CAS-038) failed in the full integration run and passed in isolation; they hit a real database and look timing-dependent. Not CAS-056.
