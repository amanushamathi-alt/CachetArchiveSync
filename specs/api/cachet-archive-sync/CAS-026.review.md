### Independent judgment on the audit-log omission (§12)
Read `CACHET_UIUX_Design_Specification_v1.md:344`, which is the BRD-adjacent doc the spec cites for
FR-23's scope: *"Every search execution, quarantine action, and permanent-delete action appears"* [in
the audit log]. `GET /tasks`, `GET /tasks/{taskId}`, and `GET /tasks/summary` are plain reads of
already-durable state — they fit none of the three named categories, and this project already has an
established, working precedent of leaving reads unaudited (`GET /audit-log` itself, `GET /quarantine`
per `CAS-008`/`CAS-009`). Agreeing independently with the spec's position here.

`POST /tasks/mark-viewed` is the one write in this set, and deserves closer scrutiny than the read
endpoints. It mutates exactly one column (`dbo.users.task_manager_last_viewed_at`) for the calling
user's own row, has no effect on any file, task-queue row, B2 object, or another user's data, and is
not reversible-risk in the way Permanent Delete/Purge are — there is no plausible forensic scenario
where "did user X open the Task Manager screen at time T" is a fact an auditor investigating a
file/task/security incident would need from `dbo.audit_log` rather than, if ever needed, from
`dbo.users.task_manager_last_viewed_at` itself (which the column already durably records). This
review's independent conclusion agrees with the spec's: this is UI-state bookkeeping, not one of
FR-23's audited categories, and not auditing it is a defensible, deliberate choice rather than a
gap. (Reviewer note: the spec text at §12 says "FR-23 names four audited action categories" while the
one document quote it cites names three — search/quarantine/permanent-delete. This is a minor,
non-substantive wording inconsistency in the spec's own prose, not a functional gap, and does not
change the conclusion above either way.)

### V4/V5 precedence (403 vs 404) — independently verified
`TaskDetailService.GetAsync` (`TaskDetailService.cs:32-42`) checks existence first (`task is null` →
`NotFound`), then ownership (`task.SubmittedByUserId != actingUserId` → `NotOwner`) — necessarily in
that order, since ownership cannot be evaluated on a row that was never found. This exactly matches
`CAS-016`'s existing `Restart` action's same NotOwner-vs-NotFound posture (confirmed by reading
`TaskManagerController.cs`'s `Restart` action, which uses the identical precedent). By design, a
non-owned-but-existing `taskId` returns 403 rather than 404 — which does confirm the id's existence to
the caller, a fact the spec's §6.2 prose itself acknowledges ("though here there's no status to hide,
just ownership"). This is a pre-existing, precedented product decision (`CAS-016`), not a new gap
introduced by this spec.

### `dbo.task_queue_summary_get`'s single-pass rewrite — independently verified
Read `Database/CachetArchiveSync/Stored-Procedures/dbo.task_queue_summary_get.sql` and the migration
file's copy of the same body: both now use one `SELECT` with two `SUM(CASE WHEN ...)` expressions over
a single scan of `dbo.task_queue` (lines 37-41 of the mirror file), rather than two independent
`COUNT(*)` subqueries. This does close the two-independent-reads race the log describes (a `Worker`
status flip landing between two separate scans could previously drop a row from both counts
transiently) — a single-pass conditional aggregation reads every row it touches exactly once. Confirmed
correct.

### Independent judgment: `src/Cachet.ArchiveSync.Web/Data/UserRepository.cs` (touches.ui: false)
This file was read in full. `IUserRepository` is a single, shared `Core` interface implemented twice:
once by `Api`'s Dapper-backed `UserRepository` (the real implementation for every method) and once by
`Web`'s own `UserRepository`, which exists *solely* to serve `CAS-002 §6.3a`'s session-revocation
check (`GetSessionTokenVersionAsync`) inside Web's own `OnValidatePrincipal` — every other member on
Web's copy is a deliberate `NotSupportedException` stub, and this pattern already existed before
CAS-026 for `GetByUsernameAsync`, `GetByIdAsync`, `IncrementSessionTokenVersionAsync`, `InsertAsync`,
`UpdateAsync`, and `SetActiveAsync` (several of those added by earlier, also `touches.ui: false`,
specs — e.g. `CAS-020`). Because `CAS-026` adds `MarkTaskManagerViewedAsync` to the shared interface,
Web's implementation would not compile without also implementing (or stubbing) that member — this is
an unavoidable consequence of one interface having two implementers, not a design choice CAS-026
introduced. The added stub follows the exact same shape, wording convention, and
`NotSupportedException` rationale as every pre-existing stub in the same file. This review's
independent conclusion: this is a justified, minimal, in-pattern fix to keep the solution building
(confirmed necessary — see §9 below, the solution does not build without it), not a scope violation.

### Note: §17 Graph Impact did not predict this touch
§17's "Communities / Modules Affected" states: *"Api project only. No Web, Worker, or Core-interface-
breaking change."* Taken literally, this is inconsistent with the spec's own Files Changed table,
which lists `src/Cachet.ArchiveSync.Web/Data/UserRepository.cs`. The change itself is justified (see
above) and is disclosed and explained in the Implementation Log, so this is not a hidden or

prediction, worth correcting for the next spec that reads §17 as a checklist. Flagged in §6 below as
well, per the reviewer checklist's explicit instruction to check for this.
