## 10. Reviewer Notes

- **N1 — HttpClient timeout is silent (minor, §2 deviation).** `TriggerMirrorSyncAsync` catches only `HttpRequestException` (`razor:1435`). An HttpClient timeout raises `TaskCanceledException`, which inherits from `OperationCanceledException`. That exception escapes to the outer `catch (OperationCanceledException)` in `PollActionAsync` (`:1416-1419`) and is treated as "disposed/superseded". The result is no warning log and no "could not be refreshed automatically" message, although §2 requires both when the Api is unreachable. `SubmitSyncActionAsync` (`:1299`) and the poll (`:1358`) already catch `TaskCanceledException`. Suggested fix: add `catch (TaskCanceledException ex) when (!ct.IsCancellationRequested)` to the same handler.
- **N2 — Malformed or empty 202 body faults the fire-and-forget task (minor).** `ReadFromJsonAsync<TaskSubmittedResponse>` (`razor:1446`) throws `JsonException` on an empty or invalid body. Nothing catches it, so the discarded `_ = PollActionAsync(...)` task faults: no toast, no log, and the exception is unobserved. The panel reload has already happened, so the Copy outcome is unaffected. The `submitted is null` branch is only reached when the body is the literal JSON `null`. The existing poll at `:1385` has the same pre-existing pattern. Low risk, because the Api always returns `TaskSubmittedResponse` on 202.
- **N3 — Disposal race at `razor:1409` (minor).** `state.Cts.Token` is read after `LoadPanelAsync`, which takes no cancellation token. If the page is closed during that reload, `DisposeAsync` (`:1517-1522`) has already disposed the CTS. `CancellationTokenSource.Token` then throws `ObjectDisposedException`, which is not an `OperationCanceledException`, so it escapes the fire-and-forget task unobserved. There is no user impact because the page is gone, and as §2 requires, no mirror sync is triggered. Capturing the token once at the top of `PollActionAsync` would avoid this.
- **N4 — Re-entrancy is handled acceptably.** `IsInFlight` is cleared before the trigger (`:1402`), so the user can start another Copy while 409 retries run. The new `PollActionAsync` cancels the old CTS (`:1341`), which ends the old retry loop silently, and the new Copy triggers its own mirror sync when it completes. This is correct, but it means the first Copy's mirror-sync attempt is dropped without a message. No component is left in a broken state.
- **N5 — Toast semantics.** Every mirror outcome overwrites the shared `toastMessage` (the "N file(s) submitted." text). On 401 the toast is left as it was and only the session-expired banner appears, which is consistent with V9.
- **N6 — Copy `Completed` with 0 files succeeded still triggers a full sync-folder scan.** This is harmless and consistent with §2 and §14 (cost accepted), but it is wasted work.
- **N7 — Two open tabs.** If two tabs both resume the same Copy, they each call the endpoint. The second gets 409 and retries until it succeeds, which starts a second, redundant full sync. This follows from the V2 design and is acceptable, but it is worth knowing for production bucket sizing (§14).
- **N8 — Test timing.** SC-2 and SC-3 use `Thread.Sleep(1500)` for negative assertions. This is tolerable with a 1 s interval, but a slow CI agent could produce a false pass, never a false fail. Waits use a 30 s `PollWaitTimeout`. All 7 tests passed in the reviewer's run.
- **N9 — Prerequisite.** Spec §14 requires CAS-059, which is present on disk. Deploy CAS-059 together with this change or before it.
