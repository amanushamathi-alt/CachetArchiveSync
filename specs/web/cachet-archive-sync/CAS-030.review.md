## 10. Reviewer Notes

**N1 — The reloaded "Failed" banner shows raw JSON (medium, UX).** Both pages append `task.ResultDetail` to the failure banner as-is (`KeywordSearch.razor:100,436`; `ODriveSyncContentScan.razor:67,435`). The Worker and the CAS-028 sweep store `result_detail` as serialized JSON, for example `{"FilenameMatchCount":null,"ContentMatchCount":null,"ExcludedCount":null,"FailureReason":"Unhandled error during Keyword Search processing."}` (`KeywordSearchTaskProcessor.cs:206-209`, `ContentScanTaskProcessor.cs:133-136`, `dbo.task_queue_sweep_interrupted`). Users will see that JSON text in the banner. The content is not sensitive, since it consists of fixed strings (design §9.2), and it follows §6/§8.2's "as is" wording to the letter. The SC-11 tests use plain-string fixtures ("Mirror directory unavailable."), which hides the problem. Recommendation: show only `FailureReason`, either by projecting it in the service or by parsing it in Web, through a small spec clarification.

**N2 — The §14 claim that "the deployed Api keeps working" after the migration is likely false (medium, rollout; PLAUSIBLE, not run by the reviewer).** `TaskQueueRepository.GetAsync` maps `dbo.task_queue_get` into a positional `record GetRow(...)`. Dapper's constructor mapping picks a constructor whose parameter count equals the column count. So an Api binary built **before** CAS-030 (a 12-parameter `GetRow`), running against the migrated procedure (13 columns), would be expected to throw on every `task_queue_get` call: search results, sync results, quarantine add, and sync actions. That would last until the new Api is deployed. The Worker is not affected, because it never calls `GetAsync`. Recommendation: treat migration and Api as one deployment unit, or apply the migration immediately before the Api deploy. Correct §14 step 1 as well. CAS-029's earlier additive change carried the same risk.

**N3 — A search or scan submitted in the current session is never acknowledged when it finishes in place (low, spec ambiguity).** `ackEligibleTaskId` is set only for tasks resolved through `GET /tasks` or `GET /tasks/{id}`. `HandleSearchAsync` and `HandleRunScanAsync` clear it. This matches §8.5's condition list exactly: condition 2 requires the task to have been resolved through those endpoints. But §8.5's prose says "watching an in-progress task finish in place" should also count. As built, a user who submits and watches a task finish still sees it in the badge until the next time the screen opens, when it is acknowledged. The spec should state which behavior is intended.

**N4 — Screen poll loops stop on 5xx (low).** In the screens' results poll loops, a 5xx sets the generic banner and ends the loop (`KeywordSearch.razor:689-696`; `ODriveSyncContentScan.razor:692-699,903-910`). This is CAS-022/023 behavior, and V10's "On Failure" column defers to CAS-022 §8.5. However, V10's rule text says the screen "retries on the next tick", and over a full-day task one 5xx now ends automatic population until the page is reopened. Reopening does repair it through the reload. Consider continuing to poll on 5xx in a follow-up.

**N5 — Minor observations (informational).**
- The aria-live text "A task has finished." is never cleared, so a second finish in the same circuit produces no new announcement, because the text does not change.
- Both pages use `@rendermode InteractiveServer` with default prerendering, so the reload's GET calls, and a short-lived poll loop for Running tasks, also run during the prerender pass. The acknowledge correctly runs only in `OnAfterRenderAsync`, which is interactive-only. Cost at 3–4 users is negligible.
- The acknowledge procedure's `updated_by` is written as `"api-svc"`, the existing process-identity convention, not the username. Attribution can still be inferred because only the submitter can acknowledge.
- The KeywordSearch reload-then-poll path sets `taskState="Failed"` without `failureDetail` when a Running task later fails. The banner has no detail in that case, which is consistent with CAS-022.

**N6 — Coverage below the §13 85% target (low).** This is self-reported in the Implementation Log (77.1% overall; `TaskQueueRepository.cs` 51% for the whole file). The CAS-030 methods themselves are about 97% covered. Record the waiver explicitly, or add repository tests for the older methods.
