## 10. Reviewer Notes

1. **Self-disclosed polling-target deviation — independently verified, confirmed correct and
   necessary.** The spec's Implementation Log and inline code comments (razor:515-525) state that
   `GET /sync/{taskId}/results` 404s for any non-`ContentScan` task type, forcing Copy/Update/Purge
   action poll loops to re-query the **original scan's** `taskId` rather than each action's own
   returned `taskId`. Verified two ways:
   - **Server-side:** `SyncScanService.GetResultsAsync` (`SyncScanService.cs:81-85`) returns
     `TaskNotFound` when `task.TaskType != "ContentScan"` (line 16) — the 404 claim is accurate.
     Given §4 explicitly forbids any Api/Core/Worker change for this spec, extending the endpoint
     was not an available alternative within scope; the deviation is a necessary, correctly
     diagnosed adaptation, not a misdiagnosis or a workaround for a self-inflicted bug.
   - **Client-side:** `PollActionAsync` (razor:528-608) queries `sync/{scanTaskId.Value}/results`
     (the scan's own taskId) and applies `ApplyProgress` against the matching per-`fileId`
     `syncStatus` in the returned panel. No residual/dead reference to polling an action's own
     `taskId` was found anywhere; `submitted.TaskId` from the action-submit response is read only
     for the log line (razor:500-502), never used to poll. Implemented completely, not partially.
   - **Process note:** the spec's §8.4 body text itself still reads as if action polling uses "this
     action's own `taskId`" — only the appended Implementation Log flags the correction. Recommend
     a follow-up edit to §8.4 itself so a future reader who doesn't reach the log isn't misled.
2. **Minor documentation gap:** the Implementation Log's "Files Changed" table lists only
   `ODriveSyncContentScan.razor`; it omits `FakeODriveSyncApiHandler.cs` (new test-double file) even
   though the "Tests Added" table separately lists the test methods that depend on it. Cosmetic —
   does not affect the verdict.
