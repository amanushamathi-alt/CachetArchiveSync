## 10. Reviewer Notes

- N1 (medium-low, real defect): `PollTaskAsync` restarts itself from `CancelSearchAsync` (:1580). The old loop reads the shared fields `pollCts`/`pollTimer` after each await (`pollCts.Token` at :1454/:1467/:1495, `pollTimer.WaitForNextTickAsync(pollCts.Token)` at :1447) instead of locals. If the user confirms Stop while the old loop is mid-GET, that GET is cancelled with a `TaskCanceledException`, which the inner catch (:1456-1462) swallows with `continue`; the old loop then waits on the NEW timer with the NEW token, so two loops poll. `PeriodicTimer` allows only one concurrent waiter, so the second `WaitForNextTickAsync` can throw `InvalidOperationException` in a fire-and-forget task (only `OperationCanceledException` is caught), or both loops run and double-process the terminal result. The window is one HTTP round-trip every poll interval, so it is rare, and the pattern pre-exists, but the 2 s restart makes it reachable. Fix: capture `var cts`/`var timer` as locals at the top of `PollTaskAsync` and use only those (and exit the loop if `cts.IsCancellationRequested` after the catch).
- N2 (low): if the poll reaches a terminal state while the cancel POST is still in flight, `isCancelRequested` is reset by the poll, and then a 200/202 response calls `PollTaskAsync(taskId, 2 s)` again (:1580). If the user has already started a new search, that call cancels the new search's loop and polls the old task instead. Guard: only restart when `isCancelRequested && activeTaskId == taskId && isSearchInFlight`.
- N3 (low): on a 409 from cancel the button reappears (`isCancelRequested = false`) until the next poll tick (up to the 10 s interval); a second click is harmless (another 409). Spec §2.3 is satisfied.
- N4 (low): the Cancelled notice is shown through `taskNotice` (the `cachet-banner-notice` role used elsewhere); consistent with §2.10. Counts use `N0` and the wording matches §2.4/§2.5 exactly (verified by exact-string assertions).
- N5 (low): live cancelled partial results have no context header (see section 6).
- N6 (low): `EnsureMode` retries the mode radio Change for up to 5 s; the implementer attributes this to bUnit dropping a Change dispatched mid-render. If it is a genuine product race (mode change ignored while results re-render), the helper hides it. Not caused by CAS-057 code paths I can identify.
- N7 (low): V9 "plain-no-matches" is a negative assertion after `WaitUntilAsync(ResultsCallCount >= 1)` plus a renderer flush. It can fail if the code regresses to showing a notice, but the timing window is small rather than deterministic.
- N8: The full-suite ODriveSyncPageTests failure is a flaky test unrelated to CAS-057 (ODriveSync untouched). Worth a separate ticket.
- N9: Dependency order: the spec requires CAS-056 merged and deployed first; the Api controller/DTO exist on disk. Deployment ordering is not verifiable from code.
- Verified correct: filter bar stays disabled during Cancelling (`isSearchInFlight` only cleared at terminal/401/non-success); isCancelRequested and showCancelConfirm reset on every terminal path (:1477-1479, :1488-1490, :1503-1504, ResetTaskState :844-845); Completed/Failed branches unchanged except the added toast; button hidden for Files/Filename/Date; Cancelled never triggers an acknowledge call; aria-label present; confirm text exact.
