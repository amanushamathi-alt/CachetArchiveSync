## 10. Reviewer Notes

**Premise check (CAS-059 re-download of a same-size Update): verified.**

1. `SyncUpdateTaskProcessor.cs:98-106` uploads the O-Drive bytes with their SHA-1 and writes that SHA-1 into `file_index.sha1_hash`. It does not write the mirror file.
2. In `B2MirrorSyncTaskProcessor.cs:162-165`, the index SHA-1 equals the B2 `contentSha1`, so the processor calls `IsLocalCopyCurrentAsync` (`:392-433`).
3. The mirror file has the same size but an older last-write time (the old upload time). The new B2 SHA-1 is known (single-part upload), so the processor hashes the file. The hash differs, so the method returns `false` (`:418-420`).
4. The processor then downloads the new version again (`:176`). The download is verified and replaces the file atomically.

Cases where an Update can still leave stale mirror content (none caused by the CAS-063 code):
- **409 limit reached:** a mirror sync runs longer than `MirrorSyncMaxAttempts × PollInterval` (about 5 minutes by default). The user is told, and the content is refreshed by the next sync.
- **Polling stops early:** the page is closed or the session returns 401 before the Update completes. This is accepted in §2.
- **Object outside the prefix:** the B2 object name (`row.B2RelativePath ?? OdriveRelativePath`) is outside the mapping's `b2_path_prefix`, so CAS-059 never enumerates it. This is UNVERIFIED as a real case: scan rows are expected to sit under the sync prefix.
- **Mirror Sync fails for that object** (download or SHA-1 mismatch). The failure is logged, the old file is kept, and the file is retried on the next run.
- **Content search:** §1 says content search also reads the old version. Mirror Sync only refreshes the file on disk. Whether the content-search index is rebuilt from the mirror was not verified and is outside this change.
- **Unchanged content:** if the O-Drive "modified" file has identical bytes, the hash matches and the file is correctly not downloaded.

**N1 — Flaky existing test (not CAS-063):** `ODriveSyncPageTests.Test_SC5_ActionButtonsReflectOwnPanelSelectionCountIndependently` (`:318-333`) failed once in the suite and passed in 4 later runs. `CheckRowByMarker` (`:107-113`) calls `.Change(true)` outside `cut.InvokeAsync`, and the button text is asserted right away with no `WaitForState`. The test does not exercise action completion or mirror sync. Recommend a separate fix: wrap the call in `InvokeAsync` or use `WaitForAssertion`.

**N2 — Stale text in CAS-060 (minor documentation):**
- §10 SC-3 (`CAS-060...md:108`) still names `Test_CAS060_Update_DoesNotTriggerMirrorSync` as the test. It does not say that CAS-063 removed it, which CAS-061 SC-5 does say.
- §14 (`:140-142`) adds "(Added later by CAS-063 …)" but keeps the now-contradictory sentence "If added later, CAS-059 also needs a date check: an updated file of the same size is skipped today."
- §9 V1 (`:98`) and §16 (`:162`, "Update in B2 and Purge from B2 behave exactly as before (no mirror-sync call)") have no superseded note.

§5 of CAS-063 only required the SC-3 and §14 notes, so this is not a scope gap. The CAS-060 notes are accurate but incomplete. The CAS-061 notes (§2 `:48-49`, SC-5 `:111`) are accurate.

**N3 — Comment header:** the `TriggerMirrorSyncAsync` header comment (`razor:1429`) still reads "CAS-060/CAS-061". This is cosmetic.

**N4 — Concurrent completions:** Copy, Update and Purge each poll independently and each trigger on completion. If two complete close together, one call gets 202 and the other gets 409 and retries until it can submit its own run. The result is one redundant but harmless Mirror Sync. This is correct, because the second action's files may have been listed after the first run started. All outcomes write to the single `toastMessage`, so the last one overwrites earlier toasts. This matches the CAS-060/CAS-061 behaviour and was not changed here.

**N5 — "Completed" with per-file failures:** `SyncUpdateTaskProcessor` marks a task `Completed` even when every file failed (`:137-141`). Mirror Sync is still triggered. This is harmless and matches Copy/Purge.

**N6 — Test timing:** the Failed-path tests use `Thread.Sleep(1500)` to prove the absence of a call (`:131`, same as the CAS-060/061 tests). This is acceptable for proving a negative with a 1 s poll interval. It is not a source of flakiness, because a false trigger would happen right after the observed GET.
