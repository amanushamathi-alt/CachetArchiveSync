Until it ships, every open lands in the §8.5 preview-error state and downloads stay disabled (V1). This fails safely but leaves the feature unusable. The Web build must not be released to production on its own (§14 step 1).
3. **§15 item 1 was owner-resolved, not implementer-assumed.** The spec records it as "Resolved 2026-09-25 (owner direction: 'make it ready and implement')", with conditions (a) to (d). The implementation honours all four: it binds to §6.2, uses private records over the Core row types, fails safely, and adds no audit on preview. I can confirm only that the resolution is recorded in the spec; I cannot independently verify the owner's direction itself.
4. **§18 "Audit Log placeholder still disabled" is superseded.** CAS-031 has since made Audit Log a live trigger on both pages (`KeywordSearch.razor:73-78`, `ODriveSyncContentScan.razor:39-44`). The CAS-032 §13.3 narrowing was correctly adapted: `MainLayoutTests.Test_SC5` and `Test_V2` now assert that the static layout hosts no placeholder at all. This is not a CAS-032 defect.
5. **Manual browser download check (§18 item 4) is UNVERIFIABLE today.** Downloads cannot be enabled without a successful preview, so an end-to-end manual PDF/XLSX download is impossible until the preview endpoints exist. What can be verified today: the `download.js` code is correct by inspection, and bUnit asserts the `fromStream` invocation (SC-5). Repeat the manual check once the preview API spec is deployed.
6. **Stale sign-off note.** Spec §16's author note still reads "Blocked on §15 item 1".
7. **Minor, non-blocking:**

   - §8.4 step 7 (Close during an in-flight download still delivers the file) is implemented but has no dedicated test.
   - V3's code-level guard is exercised by invoking the private `DownloadAsync` through reflection. That test depends on the method's name and would break silently if the method were renamed.
