### SC Failures / Gaps
- **SC-13 (PARTIAL).** The code is internally consistent. The spec says a folder "shows checked when all its matches are selected, indeterminate when some are", and the implementation shows that only after the folder's ids were resolved through the Api. Resolving every visible folder on render would add Api calls and would conflict with V9's "resolved on demand" intent. Options:
  (a) amend the spec (§2.2/SC-13) to say the state reflects selections the user has made through that folder's own checkbox or that have been resolved; or
  (b) resolve lazily, for example when a file checkbox inside a folder changes the file count under it.
  Either way, add a test for the file-by-file case. The decision is the requester's.

## 8. Known Issues Adjudicated

- **(a) Folder checkbox state.** Confirmed. Treated as SC-13 PARTIAL (section 1). It is a display and spec-wording gap with no data risk, because file ids are always correct.
- **(b) V4 vs V7 conflict (browse 404/409).** The spec is self-contradictory. The code follows V7, which is the more specific rule and the one with a test and a working Retry. In practice the task-not-found case is already caught by `GET /tasks/{id}` before browse is called. Required: the author must amend V4 (drop "or a 404/409 from browse"). No code change.
- **(c) Flaky O-Drive and `TaskPollingOptions` tests.**
  - `TaskPollingOptionsTests.Test_V8` passed in my run. It exercises host startup and options validation and has no link to the badge.
  - `ODriveSyncPageTests` failed in 4 of 4 runs here (one failure three times, two failures once), not "1 in 3". Failures seen: `Test_SC9_ConfirmedPurge...` (`First(...)` on `.cachet-sync-modal button`) and `Test_SC8_PurgeRequiresExplicitConfirmation...`.
  - The captured markup shows the Removed panel's "Purge from B2 (0)" button still disabled after the row checkbox was clicked, so the selection was lost before Purge. That is page-internal panel state, a race between the test's click and the page's per-panel reloads (CAS-045 paged loading).
  - The badge in that markup is a plain button with no `disabled` or `title`, and the closed modal renders nothing. A closed `TaskManagerModal` makes no request and renders nothing, and `OnTaskAcknowledged` fires only on acknowledge.
  - The O-Drive test files and fake handler were last edited 10-04 21:29, before the first CAS-048 edit (00:22).
  - Conclusion: not caused by the badge or modal changes. This cannot be proven without a baseline. The gate "Tests ✓" is per-project only and is not reproducible for `ODriveSyncPageTests` today. Track the failures separately.
- **(d) Double acknowledge on deep-link open.** In the normal path there is no double ack. The modal awaits the ack, then navigates; the page reads `IsAcknowledged = true` and does not acknowledge (`ApplyReloadedContext`). The page acknowledges only if the modal's ack failed, or on a direct or bookmarked link, which is the intended retry. The Api accepts a repeat ack idempotently. The tests assert a single ack (`:538`, `:560`). Acceptable.
- **(e) "M matches in total" sums filename and content totals.** It is exact for new-mode tasks (Filename, Keyword and Date each store one match type: `KeywordSearchTaskProcessor` Keyword stores content only). For legacy tasks a file can have both a filename and a content row. The browse procedures deduplicate to one row per file (`search_result_browse_lst` ROW_NUMBER), so M can exceed the number of distinct files shown. Low impact; add a one-line spec note or compute M as distinct files. No code change is required for approval.
- **(f) 1,000 cap.** The client enforces the cap on the total selection (`ApplySelectionAsync`, including the 999-preselected test) and on single-folder resolution through the Api. The Api constant is shared from Core. The values and the "exactly 1,000 allowed" boundary match.
- **(g) Q4 reports.** The buttons are not rendered. They are commented out as "hidden by request" in `KeywordSearch.razor:227-229` and `ODriveSyncContentScan.razor:58-59`, and the corresponding tests are skipped. The CAS-044 review already recorded this as pre-existing, and the O-Drive file mtime (10-04 20:49) predates CAS-048. CAS-048 did not hide them. The spec's claim "Report buttons are unchanged and apply to all modes" is therefore unverifiable and moot. It does not satisfy §14 Q4's instruction to confirm during implementation and record `BLOCKED: reports` if a mode fails. Record the outcome in the spec log and correct Q4.

## 10. Reviewer Notes

- **Side-by-side layout.** Not in the spec: `cachet-ks-results-layout` puts the results host (flex 3) beside the Quarantine panel (flex 2, min 280px), stacking below 900px.
