| Web `GET /files/{id}/view` | ✓ | ✓ | ✓ `.RequireAuthorization("CachetAuthenticated")` | Api status mirrored; fixed HTML page plus HtmlPreview CSP on non-2xx | Header allowlist matches §8.5 exactly; Set-Cookie is never forwarded |

`Content-Disposition` construction (`FilesController.cs:159-168`):
- The ASCII fallback replaces control characters, non-ASCII characters, `"` and `\`, so the quoted
  `filename` cannot break out of its quotes or inject CR/LF.
- `filename*` uses `Uri.EscapeDataString`. I checked this against the HttpClient header parser with
  sample names such as `Report (1).pdf`, `O'Brien's*notes.docx`, `a;b=c.txt` and non-Latin names.
  The runtime escapes `'()*` (for example `%27`, `%28`, `%2A`), and the Web pass-through
  re-serializes the header unchanged.
- The Gate Notes say `'()*` are left unescaped. That is inaccurate: the output conforms to RFC 5987
  attr-char. This is not a defect.
- Caveat: I ran this probe on the .NET 9 SDK runtime. The application targets .NET 8, and I am not
  aware of this behavior differing between the two.

## 10. Reviewer Notes

- **N1: I/O exceptions during rendering are not audited.**
  - Where: a stream read failure, for example a permission or I/O error inside `ReadUpToAsync`
    (`FileContentService.cs:178, 191`), after the handle opens but before the audit write.
  - What happens: the exception propagates. The response is a framework 500 with no audit row.
  - Why it is minor: it falls outside V3–V9. No content is sent, and the handle is disposed in the
    `finally` block.
  - Suggestion: consider auditing it as `ConversionFailed` or a new `ReadFailed` reason in a
    follow-up.
- **N2: `Pragma: no-cache` does not reach the browser.**
  - Api sets it, but §8.5's forward list and "always set" list both leave it out, so the Web
    pass-through drops it.
  - The implementation follows §8.5 literally, and `Cache-Control: no-store` is the effective
    control.
  - This is a spec-internal inconsistency between §6.2/§12 and §8.5. Consider adding Pragma to the
    §8.5 "always set" list in a later change.
- **N3: `SyncScanService` maps a null id to `FileIndexId = 0`.**
  - Where: `SyncScanService.cs:167,179,190` use `?? 0` when the sync row's O-Drive or B2 file-index
    id is null.
  - What happens: clicking such a row requests `files/0`. The route constraint returns 404, and the
    modal shows "could not be found".
  - It is safe, since no audit row is written and no file is read. Rendering the name as plain text
    when the id is 0 would be a cleaner UX, but that is not required by the spec.
- **N4: the archive guard trusts declared ZIP sizes.**
  - The guard reads the sizes declared in the ZIP central directory, as §12 specifies. A crafted
    archive can under-declare them.
  - Remaining mitigations: the 20 MiB input cap, the timeout, the semaphore, and NPOI's own
    inflate-ratio checks.
  - Accepted residual risk, consistent with §12.
- **N5: coverage is 84.5% against the 85% target.** The shortfall is in defensive shutdown and
  cancellation paths of `PreviewConversionLimiter`, and in the DB-only `FileIndexRepository`.
  Consider one unit test for the limiter's host-shutdown branch.
- **N6: the Implementation Log's "Files Changed" table is incomplete.** It omits about 15 existing
  test files and the Api.IntegrationTests `.csproj` that were edited to satisfy the new `required`
  members and to link the test asset. Add them for auditability.
- **N7: the Gate Notes' `filename*` remark is inaccurate.** It says `Uri.EscapeDataString` leaves
  `'()*` unescaped. My probe (on the .NET 9 SDK runtime) showed they are escaped, so the header
  conforms to RFC 5987. See §3.
- **N8: implementer items (1)–(6) in the Gate Notes are acceptable.**
