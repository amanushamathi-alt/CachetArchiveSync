**Thread-safety of `TaskProgressReporter` (reviewed in detail):**
- The count uses `Interlocked.Increment`. Intermediate writes read it with `Volatile.Read`, so a write
  may carry a slightly higher count than the calling thread's own item. This is harmless, and the SP is
  monotonic anyway.
- **Throttle:** interval check, then the `CompareExchange` guard, then a re-check under the guard, then
  the write, then the timestamp update. The guard is released in `finally`, including on OCE. The
  timestamp is updated after a failed (swallowed) write too, so a failing database is not retried on
  every item. That is acceptable.
- **Single write in flight:** guaranteed for intermediate writes. `CompleteAsync` bypasses the guard.
  This is safe because every caller awaits all `ItemCompletedAsync` calls first (`Task.WhenAll` in
  KeywordSearch, sequential loops elsewhere). Even an overlap would be harmless, because the SP never
  lowers the count.
- **Stop after 0 rows:** `_stopped` is set once, with exactly one Warning, and every later write
  short-circuits. The job continues.
- **`_itemsTotal`** is a plain field written in `StartAsync` before any parallel lambda is created.
  Task creation provides the happens-before ordering, so it is safe.
- **`CompleteAsync` before `Completed`:** awaited immediately before `UpdateStatusAsync("Completed")`
  in all five processors, and not called on the failure path.
