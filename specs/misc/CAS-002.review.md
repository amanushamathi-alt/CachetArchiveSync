### Scope Violations
None found as unauthorized additions. One item requires an explicit judgment call, addressed below.

**`Cachet.ArchiveSync.Web/Data/UserRepository.cs` — judged a legitimate, narrowly-scoped exception,
not a violation.** Reasoning:
- The spec itself (§6.3a) explicitly requires `OnValidatePrincipal` to be "registered identically in
  both Api's and Web's `Program.cs`" and to look up the live `session_token_version` — i.e., the spec
  mandates that Web independently re-validate sessions in its own process, not merely delegate to Api
  over HTTP. A synchronous Api call from inside `OnValidatePrincipal` for every Blazor page/SignalR
  event would be a materially different (and worse — extra network hop per request, extra failure
  mode) design than what §6.3a describes, and would need its own justification the spec doesn't give.
- The implementation is maximally narrow: it exposes only `GetSessionTokenVersionAsync` (a
  single-column, indexed point read); `GetByUsernameAsync` and `IncrementSessionTokenVersionAsync`
  are explicitly `NotSupportedException` stubs so Web cannot accidentally perform login or logout
  logic itself. It reads no business data, decrypts no B2 credential, and cannot write.
- This matches Karpathy P4 (no new moving part introduced beyond what's needed) and the spec's own
  reasoning in §6.3a ("Api and Web are separate processes... `dbo.users` is already the single source
  of truth both processes read").
- **Verdict: legitimate, spec-driven exception to the clean-architecture convention, correctly scoped
  and correctly documented in the file's own XML doc comment.** Recommend the `clean-architecture`
  skill/CLAUDE.md gain an explicit carve-out note referencing this file, so a future reviewer doesn't
  have to re-derive this judgment from scratch.
