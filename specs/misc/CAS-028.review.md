## 10. Reviewer Notes

These are observations, not failures.

- **N1: unlisted file.** `src/Cachet.ArchiveSync.Core/Dtos/SweptTaskRow.cs` is a new CAS-028 file that is missing from the §19 "Files Changed" table and the §17 module list. Add it for audit traceability.
- **N2: §17 mirror count.** §17 says "2 SP mirrors". The actual count is 4 (1 amended, 3 new), as §5 and §19 state. Correct the text.
- **N3: "Cas026" naming.** The SC-1 test name `Test_SC1_Cas026Migration_…`, the array `Cas026Procedures` (`TaskQueueClaimTests.cs:45`), the trigger `trg_cas026_test_force_audit_failure` (`TaskQueueSweepTests.cs:33`), and the fixture value `cas026-durability` (`TaskQueueDurabilityTests.cs:366`) all say CAS-026 rather than CAS-028. The code matches the spec as written. Fix the spec and code together in a follow-on so that audit searches for "CAS-028" find these artifacts.
- **N4: mirror header wording.** The `dbo.task_queue_claim.sql` "Amended by" header says only that the CAS-006 form "never compiled". It omits the commented-out `ORDER BY` variant (compiles, but not FIFO) that the migration header and spec §0 describe. The `worker_instance_lock_acquire` mirror comment says a re-entrant call "returns 1", while the migration comment says `sp_getapplock` "returns 0". Both are true (one describes `@acquired`, the other `@rc`), but the wording differs. Cosmetic.
- **N5: latent test-isolation risk (pre-existing suites, not a CAS-028 code defect).** `TaskQueueClaimConcurrencyTests`, `SyncTaskQueueClaimConcurrencyTests`, and `TaskQueueRestartClaimTests` are not in the non-parallel `TaskQueueRealDbCollection`. Each one claims *any* `Queued` row in a shared database. If two of them run in parallel xUnit collections, one can claim another's seeded row, and that suite's `BeEquivalentTo(seeded)` assertion would then fail intermittently. They passed in the §19 LocalDB run. Consider moving them into the same non-parallel collection.
- **N6: §0 inference about the CAS-006 edit.** The CAS-006 migration's mtime (12:11:06 IST) is identical to every other baseline file in the tree, which suggests a bulk copy or checkout at that time. So the mtime alone cannot show when the `ORDER BY` line was commented out. The conclusion that CAS-028 did not edit the file still stands, based on its content. Only §0/§17's dating of the edit is unverifiable.
- **N7: double audit on one failure path (documented, acceptable).** Suppose the `TaskFailed` audit succeeds but the `Failed` status write then throws (`Worker.cs:314-319`). The row stays `Running` and later gets a second audit row (`TaskInterruptedByRestart`) from the sweep. This is consistent with FR-23 (no terminal status without an audit) and is covered by `Test_DispatchBoundary_StatusWriteFailsAfterAudit_…`. Operators reading the audit log may see two failure rows for one task.
- **N8: legacy test names.** `Test_ExecuteAsync_NoProcessorForTaskType_LogsWarningAndContinues` and `Test_ExecuteAsync_ProcessorThrows_CatchesLogsAndKeepsLoopAlive` still pass, but their names describe the pre-CAS-028 behavior. The V6 and SC-10 tests now own those behaviors. Renaming is optional.
- **N9: gate caveats inherited from §19.** Gates certify the combined CAS-028/029/030 tree as of 17:33–17:39 IST, not a CAS-028-only diff. `TaskQueueRepository.cs` is below 85% whole-file coverage because it is real-DB-only. `endpoints diff` was not run; the manual check substitutes for it. The reviewer did not re-execute any of these.
