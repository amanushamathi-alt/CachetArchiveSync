# Review Report - CAS-054

## Verdict: APPROVED WITH NOTES

The implementation matches the spec on every point that matters for correctness:

- The watermark is contiguous.
- Every disposition path reports completion to the tracker.
- Skipping is exactly `file_index_id <= W`.
- `task_queue_restart_ins` is atomic, and its ownership checks precede the carry-over.

## 10. Reviewer Notes

Not blockers. N2 and N3 should be triaged by the team.

- **N1 (verification gap):** all DB-backed CAS-054 tests (V1, V2, V3, V6, V7, SC-2, SC-3, SC-7, SC-11) are `Skip`-marked. The implementer states they passed against a local DB; I did not run them. The SQL reads correct, but the SP-side claims rest on that stated, unverified manual run.
- **N2 (SC-10 robustness):**
  - **(a) New Worker + old DB:** `UpdateResumeWatermarkAsync` fails on every candidate completion after the first 10 s. The failure path does not reset the interval (`Processor:194`), and there is no back-off or give-up. The in-flight guard serialises the calls, so there is no storm, but it means one failed DB round trip plus one warning per completed candidate, potentially hundreds of thousands of warning lines on a 310k search. The task still completes. Suggest a circuit-breaker after N consecutive failures, or interval reset on failure.
  - **(b) New Api + old DB:** `RestartAsync` always passes the three new parameters, so the old `task_queue_restart_ins` would throw "too many arguments". Restart would fail outright until the migration is applied. §10 SC-10 names only Worker pairings, so this is outside the written criterion, but §12 says application and migration deploy independently. Treat the Api as deploy-after-migration, or document it.
- **N3 (SC-5 progress presentation):** the skip catch-up is O(skipped) in-memory `Interlocked.Increment` calls with at most throttled DB writes, so cost is negligible. But the first persisted write is `(0, total)` and the skipped count first appears at the next throttled write, so Task Manager briefly shows 0/total on a resumed task. This is cosmetic, but it contradicts the "starting at the skipped count" intent. The test asserts the `(0, total)` first write, so it is a known, accepted behaviour.
- **N4 (test depth):**
  - SC-1 at processor level is serial with an always-elapsed clock.
  - `Test_DefectProbe_WatermarkAdvancesPastDroppedContentCandidates` is a good regression guard for the earlier bug where dropped content candidates did not report completion. In the delivered code all three disposition branches (no-term at `:236`, non-match at `:253`, end-of-switch at `:348`) route through `CompleteCandidateAsync`. The "DefectProbe" name is stale and could be renamed.
- **N5 (V7 failure mode):** an out-of-range `Worker:ResumeMaxAgeHours` throws from the `TaskManagerService` constructor. The service is registered scoped (`Api/Program.cs:254`), so the failure surfaces as a 500 on the first Task Manager request rather than at host startup. It also breaks the whole controller (list, get, acknowledge), not just restart. Consider validating the option at startup (for example `ValidateOnStart`).
- **N6 (unflushed watermark):** the watermark is throttled to 10 s and is not flushed on normal completion or on the failure path, so up to about 10 s of progress can be re-done after a crash. This is acceptable and matches §2.2.
- **N7 (counts):** `ResumedFromTaskQueueId` is derived from `task.RestartedFromTaskQueueId` and is non-null only when the watermark is non-null. A restart that was not resumed (full restart) correctly reports null. Match counts are re-read via `search_result_lst`'s `@totalCount`, which counts all rows for the task with no `is_active` filter, so carried-over rows are included.
- **N8 (shared ids):** the tracker steps back over a trailing run sharing the next candidate's `file_index_id`, so W never lands between a Filename and Content row of the same file, and `<= W` resume stays exact. In Keyword mode only Content rows exist anyway.
