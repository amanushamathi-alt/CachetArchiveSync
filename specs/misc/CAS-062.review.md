### Name-rule analysis (`IsSafeObjectName`, `B2MirrorFileRemover.cs:98-107`)

| Case | Result | Severity |
|------|--------|----------|
| `\`, control chars, `<>:"\|?*` | Refused | — |
| Empty, `.`, `..` segments; `//`; leading `/` | Refused | — |
| Trailing `.` / space (incl. segments made only of dots or spaces) | Refused | — |
| ADS `::$DATA`, drive-relative `C:x`, `\\?\` long-path prefix | Refused (`:` / `\`) | — |
| Leading spaces | Accepted. Win32 does not trim them, so no folding. | None |
| Reserved device names (`NUL`, `CON`, `COM1.pdf`, `nul.txt`) as the last segment | On this Windows 10 19045 host, `GetFullPathName` gives `\\.\NUL` / `\\.\COM1` (probed). That fails containment, so `Failed` and nothing is deleted. In a directory segment (`CON/a.txt`) the name stays a normal path. A file with a reserved name cannot exist on NTFS through Win32, so there is no folding onto another object. Newer Windows builds may resolve these names differently; not verified. Either way the result is `Failed` or `NotPresent`. | Info |
| Unicode / full-width / NFC vs NFD | NTFS does not normalize, so different forms are different files. The upcase table folds full-width letters only by case, which is the same as S-2. | Info |
| **8.3 short names** (e.g. `D/Shares/LONGFI~1.PDF`) | **Accepted.** If 8.3 name generation is on for the mirror volume, the name resolves to `longfilename.pdf`, a different object's mirror file, and deletes it (S-1). | **Low** |
| Case-only difference (`A.pdf` vs `a.pdf`) | Accepted; deletes the other object's copy. Known and accepted as S-2. | Low |

### Findings

- **S-1 (Low, new): 8.3 short-name alias accepted.** A B2 object whose segment looks like an 8.3
  alias (`NAME~N.EXT`) can delete a different object's mirror file when 8.3 generation is enabled on
  the `b2_mirror_root_path` volume.
  - Why Low:
    - B2 keys normally come from Windows O-Drive files, and Windows will not create a long name that
      collides with an existing short alias in the same folder.
    - The action needs `CachetFullAccess` and confirmation.
    - The damage is limited to a cache copy inside the mirror root. Mirror Sync (auto-run after Purge
      by CAS-061) downloads the other object again, because `IsLocalCopyCurrentAsync` fails.
    - 8.3 generation is off by default on non-system volumes in current Windows Server. Its state on
      `svsws10` was not verified (`fsutil 8dot3name query` needs elevation).
  - Optional fix: after resolving the path, confirm that the final segment's real on-disk name equals
    the requested segment, by enumerating the parent folder for that exact name. This closes S-1 and
    S-2 together. Alternatively, refuse segments matching `~\d`.
- **S-2 (Low, known):** case-only aliasing, as above. Already accepted in the Implementation Log.
- **S-3 (Low, known):** time gap between `TraversesReparsePoint` and `File.Delete`. Exploiting it
  needs write access to the mirror share. Same pattern as `MirrorFileReader`.

## 10. Reviewer Notes

- **N-1 (Low, operational; spec-conformant):** In Permanent Delete, a name refused by V6 always
  returns `Failed`.
  - Some of these names cannot exist as a local file at all (`<>:"|?*`, control characters). For
    those, every retry ends in `local-delete-failed` and the `quarantine_entry` stays `Active`
    forever, although B2 and `file_index` are already done.
  - The workaround is CAS-014 "Remove Item".
  - Purge writes a `SyncActionFailedLocal` row for such names, which is harmless.
  - Option: return `NotPresent` for names Windows cannot store, and keep `Failed` only for names that
    fold onto another file (`\`, trailing `.`/space, `//`, `./`). This needs a spec decision.
- **N-2 (Low, pre-existing pattern):** In Permanent Delete, the new `DeleteFailedLocal` audit write
  (`QuarantinePermanentDeleteService.cs:235`) is not guarded. If the audit store throws there, the
  exception leaves the batch: later files are not processed and the request fails.
  - This matches the existing step-2 audit (`:192`) and the accepted N-3/N-4.
  - V5 for PD is worded around "an unexpected error from the remover", so this is not an SC failure.
- **N-3 (Info, pre-existing):** In Purge, if the soft-delete, the `Synced` write or the success audit
  throws after B2 is purged, the per-file catch marks the file `Failed` and the remover never runs.
  The local copy then stays, which is the CAS-007 behavior.
- **N-4 (Info):** The interface returns a `B2MirrorRemoveResult` record, not the bare enum named in
  §5. This is a faithful realization of §5; consider aligning the §5 wording.
- **N-5 (Info, test weakness):** `QuarantineEntryForDeleteRow` has no source field, so
  `Test_CAS062_PermanentDelete_ODriveRow_RemovesB2MirrorKeyOnly` is effectively SC-10 with another
  `FileIndexId`. The guarantee comes from the structure (no O-Drive dependency, hard-coded `B2`
  source) and from SC-5.
- **N-6 (Info):** If an `IB2MirrorFileRemover` returned `null`, the code would throw a
  `NullReferenceException` outside the guarded call (`SyncPurgeTaskProcessor.cs:178`,
  `QuarantinePermanentDeleteService.cs:233`). In Purge that marks the file `Failed`. The real
  implementation never returns null.
- **N-7 (Info):** Mirror Sync's `InvalidPathReason` (`B2MirrorSyncTaskProcessor.cs:342-374`) does
  not reject a trailing `.` or space, but the remover does.
  - So Mirror Sync can write `b.pdf.` to local `b.pdf`, and Purge of `b.pdf.` then reports a local
    failure instead of deleting.
  - This is the safe direction. Mirror Sync is out of scope (§6).
- **Verification plan §16 (manual)** is still open and needs to be done on `svsws10`. Also run
  `fsutil 8dot3name query <mirror volume>` there (elevated) to settle how much S-1 matters.
